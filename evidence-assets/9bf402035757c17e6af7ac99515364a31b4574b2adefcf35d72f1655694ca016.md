# 保存与复查同一次计算 / Calculation-version records

LunaMargin 的 JSON 证据格式现为 **schemaVersion 3**。它保存地点与具体点位、任务条件、指标、失败原因、窗口、压力测试，以及实际使用的算法和数据字节。

## 版本如何绑定

- `calculationBuildId`（兼容字段 `buildId`）定位计算版本；`interfaceBuildId` 单独记录生成导出时的界面版本。恢复历史计算时，当前界面和原算法可以不同。
- 计算版本是应用源文件、算法、三个数据包和方法标识组成的内容摘要，**不是 Git 提交号**。源码文本按仓库的 LF 换行规范归档，科学数据保留原始字节。每个版本在 `evidence-assets/build-<SHA-256>.json` 有可检索清单。
- 算法与数据以自身 SHA-256 命名并保存；旧文件不被新版本覆盖。构建标识由当前实际内容重新计算，没有固定的历史哈希常量。
- 浏览器核对清单与输入字节，再从**同一份通过校验的算法文本**加载计算模块。搜索和图表也使用该算法。上传记录中的 JavaScript 仅作为保存的源码检查，绝不执行。
- JSON 内嵌数据包与算法原文，适合离线保留；HTML 显示两种版本及稳定快照入口。托管快照缺失时明确报错，不保证外部托管永久存在。

生成与核对：`node scripts/build.mjs`、`node scripts/check.mjs`。构建使用 [prepare-release.mjs](../scripts/prepare-release.mjs)，检查会验证当前输入、全部保留版本和快照字节。静态构建产物包含相同快照。现阶段设备高度仍只有 **2 m**；记录要求其他高度时拒绝恢复，不静默替换为 2 m。

## 用户如何恢复

1. 分享链接带有计算版本、算法和数据摘要。存在且通过校验的原版会被恢复；历史计算模式明确显示“当前界面、原算法和数据”。
2. 在导航仪结果卡展开“计算版本与已保存记录”，选择“打开已保存的 JSON 记录”。先展示文件中保存的旧结果，并核对快照。
3. 原版可用时可以恢复原计算。原版缺失时保留文件中的旧结果；只有用户明确选择，才使用当前版本开展新计算，并显示重算状态。

## 格式兼容

| 格式 | 行为 |
| --- | --- |
| schema 3 | 要求有效的构建、算法和数据摘要；验证内嵌快照；按原版恢复或明确报告缺失。 |
| schema 1 / 2 | 可打开旧记录；未保存版本字段时显示“版本未知”，不能声称复现原计算。可以明确选择用当前版本新算。 |
| 未支持的未来格式 | 明确拒绝，避免错误解释字段。 |

CSV 保留每行实际值 `longest_darkness_hours`、`longest_earth_gap_hours`、`joint_visibility_hours`，并加入三个任务阈值 `maxDarkHours`、`maxCommGapHours`、`minJointHours` 和版本摘要。原先容易混淆的实际值列 `max_darkness_hours` / `max_earth_gap_hours` 改为 `longest_*`。30 条中心/样本记录可单独根据实际值和阈值核对判定；CSV 不承担重新计算地形的作用。

## 验证证据

[纯函数检查](../tests/provenance.test.js)覆盖同版、算法/数据变化、缺失、篡改与旧格式。[构建产物行为检查](../tests/round2-version-browser.mjs)真实执行不同的合成算法和数据版本，验证主计算、搜索、旧结果保留、明确重算和 CSV 判定；所有反例只存在于隔离的测试响应或内存中，未写入 NASA 数据。
